# Booking options and recovery preparation — 0.5.0

Prepared 18 November 2026. This phase builds on the verified 0.4.0 source `5b6a0bdbc9a776cbc6cd3ef984c07ff61918847d`. It does not activate supplier production, change merchant credentials, submit Google Play content or demonstrate complete native booking/payment.

## Customer-visible behavior

After a successful room-price check and acceptance of any changed terms, the review offers an optional booking-options screen. It shows the same selected stay and supplied taxes/cancellation conditions, and signed-in customers can explicitly request a server-checked charge amount. The original direct website action remains the primary action in the default build, so the new optional screen does not force an extra website-handoff step.

**Native payment creation is disabled by default**, independently of server readiness. The shipped preparation view collects no traveler names, email, phone or special requests. It explains that traveler details and payment are completed on the Remal website, where the offer must be selected and checked again. Search, saving, comparison and the established website handoff remain available.

The full traveler/contact/review/status presentation and its state engine are implemented for isolated fixtures and later validated activation. Every adult/child occurrence and original child age is retained. Lead names map to the first adult in the first room; international phone digits normalize without changing their value. Names, contact, comments, quote/offer/status capabilities and hosted-payment links remain in RAM. No card fields or merchant/supplier keys are introduced.

## Financial and ownership boundaries

- The review retains its returned `p-` offer and signed prebook context privately, separate from the existing search-only website URL. A pure imperative getter rechecks the current draft, owner, search, accepted terms and existing five-minute selection/two-minute checked-view limits. Rechecking, changing selections or signing out invalidates old authority.
- Read-only availability/quote/recovery/status adapters accept the backend's exact bare envelopes without relaxing the success-envelope rule for existing endpoints. They validate the expected sandbox/production mode, exact decimal amount/currency, bounded expiry and HTTPS Ziina payment URL scope. A booking confirmation also needs the server's verified-payment flag and supplier reference. Browser opening, dismissal and redirect parameters never establish success.
- Authentication is pinned privately before an asynchronous mode check, preventing an old traveler payload from being sent using a newly switched account's session. Status uses its separate scoped capability and cannot invalidate an unrelated user session.
- Checkout creation is single-flight. A cryptographically random idempotency key is stored before dispatch. A timeout, malformed/lost response, cancellation after dispatch, missing recovery result or uncertain supplier/payment result remains unknown; it never causes an automatic create replay or a fresh-key retry.
- Only `{version, environment, ownerDigest, idempotencyKey, createdAt}` can enter the recovery marker. The digest is account-linked pseudonymous data derived from the verified email and environment, not an anonymity claim. Native uses existing [Expo SecureStore](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/); web-preview recovery is RAM only and web financial creation remains disabled. No traveler payload or payment/offer capability is persisted. Errors do not fall back to insecure storage.
- The new authenticated backend recovery operation reads an existing attempt by idempotency key and current owner/realm. It never creates a supplier form, payment intent or booking. Unknown/wrong-owner/wrong-realm lookups reveal no record. Recovery remains available when new checkout creation is unavailable, and expired payment URLs are omitted.
- Foreground recovery only checks existing state. Before opening a payment page, the controller checks the current server-owned attempt again. A user with an unresolved existing request must not be routed into a second payment from the preparation screen. Clearing a safe completed marker also retires the original review draft.

Native SecureStore is not an account-wide recovery catalogue. Uninstallation, device loss, cross-device operation and lost credentials require additional account/support recovery work before financial activation. Device behavior, payment return handling and real financial reconciliation remain separate release gates. The local marker is not the source of truth for bookings.

## Authentication correction

Previously, a network failure while restoring a saved session could render a signed-out account while the transport continued using the cached credential. The credential is now quarantined from requests after failed validation; an explicit retry can read the encrypted stored credential again. Explicit logout still revokes/deletes a quarantined credential. Dedicated offline regressions cover restore failure/retry, storage failure and logout.

## Dependency advisory

The compatible new module is `expo-crypto` 58.0.8, used for UUIDs and the local owner digest. The dependency audit on 18 November reported a high-severity advisory for installed `picomatch` versions 2.3.2/4.0.7, propagated through many Expo/build-tool dependency paths. This is one root advisory, not that many independently discovered application defects. The [reviewed advisory GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf) and [upstream releases](https://github.com/micromatch/picomatch/releases) listed no patched version when inspected. No forced dependency upgrade, invented patched version, SDK downgrade or successful-remediation claim is made. Track upstream and assess build-tool pattern exposure before production; this audit is not a full application security assessment.

The build remains local, using the existing CNG/SDK/JDK/Gradle helper and no Expo account or cloud build. Generated Android/iOS files are not hand-edited. Production keys/AAB, physical-device validation, supplier/merchant activation, privacy/deletion fulfillment and Play review remain pending.
