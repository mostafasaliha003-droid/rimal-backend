## Release blockers

- Online collection is disabled by default. Keep `PAYMENT_ROLLOUT_APPROVED`, `PAYMENT_PRODUCTION_APPROVED` and `PAYMENT_CHECKOUT_ENABLED` unset or false on the existing Render service until certification and explicit business approval. The local code now has separate Sandbox and Production gates for a durable verified checkout, supplier fulfillment, official voucher delivery, cancellation and customer refund; the presence of a gate does not certify the account, provider permissions, SMTP delivery, webhook proxy, real MongoDB concurrency or live financial behavior. Do not enable collection simply to make the button work.
- Legacy payment and booking endpoints return HTTP 410 because they accepted client-provided payment confirmation. Integrations using them must migrate to the verified lifecycle before reactivation.
- A payment return URL is never proof of payment. The frontend shows a pending-verification message and retains its session draft. It does not claim a confirmed booking or automatically retry a charge.
- Credentials previously embedded in server source must be rotated at the providers, including email, database and any reused admin credential. Removing source values does not erase Git history. Set `SMTP_USER`, `SMTP_PASSWORD`, `MONGO_URI`, and an appropriate `ADMIN_PASSWORD_HASH` securely in the deployment environment. Never put secrets in `VITE_*`: those values are public browser configuration. The existing frontend API key is not user authentication.
- Have the business approve and publish legal terms, privacy policy, refund rules and support contacts. No invented legal policy, ratings, cashback, room amenities or cancellation promise has been added.
- The deployed supplier rejected AED rate searches with `invalid_params: unknown currency`; a controlled USD search returned HTTP 200 with USD rates. Search and room details therefore request USD through `SEARCH_CURRENCY` in `frontend/src/services/offers.js`. Comparisons and budget filters use USD, and prices retain the supplier's currency without conversion. Enable AED searches only after confirming support for the configured supplier account.
- Display estimates fetch daily USD-based AED, SAR and EUR quotes from Frankfurter's public API, cache valid quotes for six hours, and reject quotes older than five days. They include the quote date and the unchanged supplier amount. If FX is unavailable, show only the supplier amount; never convert taxes, search requests or payment payloads. These mid-market quotes are not guaranteed settlement rates and do not authorize charges in the selected display currency.
- USD, AED, SAR and EUR are accepted by the local checkout only when ETG's refreshed rate and no-card `deposit` form agree on the **exact original amount and currency**. Approximate display conversion is never a charge or refund quote. Provider approval and real test-account support for each currency remain unverified; there is no fallback to an AED conversion if a supplier or provider rejects USD.
- A Ziina redirect, webhook event or successful payment-intent `POST` is not proof of payment. Only an authenticated matching `GET /payment_intent/{id}` authorizes supplier fulfillment; only a matching `GET /refund/{id}` proves a refund completed. Do not turn on `PAYMENT_CHECKOUT_ENABLED` for an uncertified production trial.
- Validate Arabic responses and multi-room/child occupancy against the supplier sandbox. Unit/browser tests use fixtures, not live inventory certification.

## Verified Ziina checkout

The public `POST /api/payment/ziina/intent` requires the existing public API key and a stable `Idempotency-Key`; `GET /api/payment/availability` reports whether the server and MongoDB are ready. The intent response includes a reference and per-attempt access token; the browser uses that token in a Bearer header for `GET /api/payment/ziina/:reference/status`, never in a query string. Status responses and payment endpoints are not cached. A return to `/checkout` is displayed as pending until server-side reconciliation reports `booking_confirmed`; a payment failure, unverified/unknown attempt or refund has its own state, not a fabricated booking confirmation.

Preflight compares the original hotelpage dates, occupancy, hotel, room, book hash and price against the selected offer; prebooks at zero tolerated price increase and requires a matching no-card `deposit` in ETG's booking form. The attempt, supplier account fingerprint, Ziina test mode and encrypted guest details are persisted before intent creation. A timeout or unknown intent-creation result stays `intent_unknown` for manual reconciliation and **must not be POSTed again**. The worker fetches Ziina status with server credentials and checks intent ID, operation ID, account, test mode, amount, currency and zero tip before invoking ETG `finish`. It also verifies the persisted ETG account before each supplier reconciliation. ETG records a finish fingerprint before sending; ambiguous or pending supplier results are checked by status, never treated as a failed booking eligible for refund. Confirmed supplier failure creates one saved refund ID before Ziina `POST /refund`; an ambiguous refund is queried using that ID, not submitted again. A matching authenticated refund `GET` must report `completed` before the customer sees a completed refund.

After a verified ETG booking, the checkout worker retrieves the **official supplier PDF voucher** and sends it by SMTP to the encrypted guest contact; it does not generate a substitute voucher from a local template. Voucher retrieval failures retry while no cancellation has been claimed. Email is claimed before SMTP; an ambiguous SMTP result becomes `notification_status: unknown` with `action_required: reconcile_confirmation_email`, never an automatic resend. A cancelled booking cannot initiate a new confirmation email after its cancellation claim. When a matching refund `GET` confirms completion, a separate refund email is sent with the authorized amount and charged currency. Unknown refund-email delivery likewise needs manual reconciliation, not a second send. Missing contact details or expired retention require an operator to resolve the notification; provider completion and customer notification are separate statuses.

## RateHawk Booking Call List

Implemented against the [ETG booking call list](https://docs.emergingtravel.com/docs/b2b-api/booking/):

| ETG operation | Backend endpoint | Behavior |
| --- | --- | --- |
| Create booking process | `POST /api/booking/form` | Calls `/hotel/order/booking/form/` with a refreshed prebook hash; persists the partner order ID before each attempt. |
| Create credit card token | `POST /api/booking/card-token` | Calls Payota `https://api.payota.net/api/public/v1/manage/init_partners` only for a form payment requiring card data. |
| Start booking process | `POST /api/booking/finish` | Claims the saved process before submitting `/hotel/order/booking/finish/`; never resubmits a claimed finish. |
| Check booking process | `POST /api/booking/status` | Checks `/hotel/order/booking/finish/status/`; returns pending, `3ds`, confirmed or failed, without treating a redirect as confirmation. |
| Receive booking status webhook | `POST /api/v1/webhooks/ratehawk` | Enforces HMAC verification, deduplicates durable receipts and checks the supplier state before accepting a terminal outcome. |

The first four endpoints are server-to-server only. They require `Authorization: Bearer <RATEHAWK_BOOKING_TOKEN>` and JSON bodies, reject browser `Origin` requests, and never accept the public `x-api-key` as booking authorization. Responses use `Cache-Control: no-store`. Keep this private token out of frontend configuration, URLs and logs. Use a securely generated token of at least 32 characters, different from `REMAL_SECURE_KEY`.

### Request Contracts

1. Immediately after successful prebook, call `form` with `book_hash`, `language`, the actual guest `user_ip`, and the original hotelpage occupancy as `guests: [{ adults: 2, children: [7] }]`. The trusted caller must bind that occupancy and hash to the selected offer; these endpoints are not a public checkout API. Supply `Idempotency-Key` with 16-128 letters, digits, underscores or hyphens. Repeat the same key and body to recover the same process; changed inputs return 409. Save the returned `process_id`. Choose a `payment_type` from the returned `payment_types` without changing its `type`, `amount` or `currency_code`.
2. Only when that payment has `is_need_credit_card_data: true`, call `card-token` with `process_id`, `payment_type`, `user_first_name`, `user_last_name`, `credit_card_data_core: { card_number, card_holder, month, year }`, and `cvc` when required. All card fields are strings; month/year have two digits, PAN has 13-19 digits without spaces, and the documented CVC has three digits. The server uses the form's `item_id` as Payota `object_id`, generates unique `init_uuid`/`pay_uuid`, and stores only those IDs and the selected payment. Payota returns `status: ok`, not a new token string. No automatic retry or redirect is allowed. A timeout leaves `card_unknown` for operator reconciliation, not a new card attempt.
3. Call `finish` with `process_id`, the selected `payment_type`, `user: { email, phone, comment? }`, and `rooms: [{ guests: [{ first_name, last_name, is_child, age? }] }]`. Names/contact data must be real, room counts and child ages must match the saved hotelpage occupancy, and `gender` is required when the form requests it. Supply `supplier_data: { first_name_original, last_name_original, email, phone }` when required by the contract. Optional `upsell_data` entries must match form-provided `name`/`uid`; optional `arrival_datetime` must be a valid date-time. The server injects its saved card IDs when needed. Repeating the same finish data returns the existing process; changing it returns 409.
4. Call `status` with `{ "process_id": "<saved process_id>" }`. Honor `next_check_at`. Only `status: confirmed` has `success: true`; form readiness, a successful finish submission, timeout and `3ds` do not. HTTP 202 denotes an in-progress request. An HTTP error after submission is not permission to create a new booking: retain the process ID and query status.

Form retryable errors use fresh partner order IDs, with at most ten form calls. Form lifetime is conservatively limited to 60 minutes from local process creation. `finish` has neither network nor HTTP 429 automatic retries. A timeout, unknown/5xx response, missing response envelope or duplicate finish moves to status checks instead of resubmission. A crash after the durable finish claim can leave an uncertain outcome; recovery queries status and never guesses that resubmitting is safe.

The MongoDB status worker resumes saved in-flight processes when the server connects. Per-process leases serialize checks across workers and HTTP requests. It normally checks at five-second intervals, schedules a final check near the booking deadline, honors supplier rate limits, and slows unresolved checks to once per minute after the deadline. `timed_out: true` still means unresolved, not cancelled or safe to rebook. `RATEHAWK_BOOK_WAIT_MS` defaults to 90000 ms and is bounded to 5 seconds-15 minutes in the durable workflow; set the supplier-agreed window before certification. Network outages, rate limits and worker load can delay checks. Monitor long-running processes and reconcile them with ETG support.

For `3ds`, the private status response contains `data_3ds: { action_url, method, data }`. The trusted checkout must submit those supplied fields using the supplied GET/POST method, safely encoding names/values without injecting HTML, then resume server-side status checking after the bank redirect. Only HTTPS challenge URLs are accepted. Configure `FRONTEND_URL` and `RATEHAWK_RETURN_PATH` to a real, tested return handler whose host ETG has registered. The existing public checkout is NOT wired to these private APIs or a bank-challenge view; its current `/checkout/success` fallback is not a completed 3DS integration. Do not enable `now` payments before this frontend and return-path certification is complete.

### Webhook and Activation

Register `https://<backend-host>/api/v1/webhooks/ratehawk` with ETG support; the handler must be on the API host, not a static-only frontend. The required envelope is `{ data: { partner_order_id, status: "completed" | "failed" }, signature: { timestamp, token, signature } }`. Verification uses HMAC-SHA256 of the concatenated timestamp/token with `RATEHAWK_API_KEY` and a timing-safe comparison. `RATEHAWK_WEBHOOK_STRICT` no longer makes verification optional.

The documented signature does not cover `data`, so the reported outcome is not trusted on its own: the handler uses a checked process state or queries ETG. Token digests and payload digests detect modified replays; duplicate processed events return 200 without further effects. Old signed timestamps remain acceptable for ETG's delayed retries, while timestamps over five minutes in the future are rejected. No raw signature/token is stored. HTTP 200 follows durable outcome storage; invalid signatures receive 401, changed replays 409, and unresolved state or database failures 503 with `Retry-After: 30`.

This ETG booking webhook updates supplier state only and records `action_required` for payment verification or refund review. It does NOT issue vouchers, send confirmation emails, charge customers or refund them. The separate Ziina checkout worker described above can issue a single refund after a verified payment and confirmed supplier booking failure; this ETG webhook cannot. New process records do not create a customer-facing `Booking` automatically. Monitor `BookingProcess` states `creating`, `card_pending`, `card_unknown`, `finishing` and overdue `processing`/`3ds`, along with unprocessed `BookingWebhook` receipts and their action-required records. Do not delete idempotency records while a supplier order can remain actionable.

Required deployment configuration: `MONGO_URI`, `RATEHAWK_BASE_URL`, `RATEHAWK_KEY_ID`, `RATEHAWK_API_KEY`, and the private `RATEHAWK_BOOKING_TOKEN`. Existing MongoDB `_id` uniqueness and atomic updates provide request claiming; ensure the new collections and polling indexes can be created, backed up and monitored in the deployment database. Validate concurrent submissions, failover and restart behavior against an isolated MongoDB deployment before production; unit tests substitute the store.

Keep `RATEHAWK_BOOKING_ENABLED`, `RATEHAWK_CARD_TOKENIZATION_ENABLED` and `PAYMENT_CHECKOUT_ENABLED` unset or false for now. No flags or provider settings were enabled by this implementation. Disabling new bookings does not disable authenticated status checks or reconciliation of existing operations. Card tokenization requires explicit PCI approval for the entire environment, including proxies, APM, request-body tracing and crash reporting; code-level redaction alone does not make the service PCI compliant. PAN/CVC are neither persisted nor passed to the ETG exchange logger, and booking logs redact guest names/contact details, payment IDs, challenges and supplier debug echoes. Existing historical logs are not rewritten; restrict their access and follow the approved retention process.

Use the true sandbox for certification; ETG's test-key hotel `8473727` can create a real financial obligation and must not be used as an automated test fixture. Sandbox responses have documented limitations, including missing card/3DS fields and payment/currency differences. Verify supported settlement currencies, supplier contract requirements, bank challenges, guest data, cancellation/refund handling and the verified customer-payment lifecycle before activating the public checkout. These changes do not add FX conversion or turn USD offers into AED payments.

## RateHawk Post Booking

Implemented against [Retrieve bookings](https://docs.emergingtravel.com/docs/b2b-api/post-booking/retrieve-bookings/) and [Cancel booking](https://docs.emergingtravel.com/docs/b2b-api/post-booking/cancel-booking/). The ETG transports use POST `/api/b2b/v3/hotel/order/info/` and `/api/b2b/v3/hotel/order/cancel/` on `RATEHAWK_BASE_URL` with the existing Basic credentials. These calls do not use Payota or the customer's payment gateway.

All routes below require the existing private `RATEHAWK_BOOKING_TOKEN` Bearer authentication, reject browser-origin requests and send `Cache-Control: no-store`. Neither the public search API key nor a booking reference alone authorizes access. The trusted caller must authenticate the customer/operator and verify their right to the order before invoking these server-to-server endpoints.

| Backend endpoint | Contract |
| --- | --- |
| `POST /api/v1/bookings/retrieve` | JSON with optional `ordering`, `pagination`, `search` and `language`. Returns one page and ETG's `current_page_number`, `total_orders`, `total_pages`, `found_orders`, `found_pages` and `orders`. |
| `GET /api/v1/bookings/:partnerOrderId/info` | Retrieves exactly the matching `partner_data.order_id`, preserves supplier prices/policies/upsells and includes `current_penalty` when it can be determined. |
| `POST /api/v1/bookings/:partnerOrderId/cancel` | Requires explicit consent and the current penalty as described below. Records the request durably before any supplier cancellation. |
| `GET /api/v1/bookings/:partnerOrderId/cancel/status` | Reads a saved cancellation and, when due, reconciles it using order information only. Never resends cancellation. |

Retrieval defaults to `ordering: { ordering_type: "desc", ordering_by: "created_at" }`, `pagination: { page_number: 1, page_size: 10 }` and `language: "en"`. Page numbers start at 1; page size is 1-50. Sort direction is `asc` or `desc`; sort fields are `cancelled_at`, `checkin_at`, `checkout_at`, `created_at`, `free_cancellation_before`, `modified_at`, `payment_due` or `payment_pending`. Each of those dates, plus `paid_at`, can be filtered in `search` by an inclusive `{ from_date?, to_date? }` range. Other supported filters are integer `order_ids`, string `partner_order_ids`, `status` (`cancelled`, `completed`, `failed`, `noshow`, `rejected`) and the documented `source` values. Invalid or unknown filters are rejected before contacting ETG. `page_out_of_range` returns HTTP 400 rather than silently returning another page; HTTP 429 includes the supplier-derived `Retry-After` when available. There is no unbounded fetch-all loop or automatic transport retry.

ETG recommends waiting 1-2 minutes after final booking confirmation before retrieving order details. A valid empty single-order result or `order_not_found` returns HTTP 202 with `pending: true`, `order: null` and `retry_after_ms: 60000`; it does not establish a failed or cancelled booking. Invalid or mismatched supplier responses are rejected. Lists retain both total and filtered counts without treating the account-wide total as the matching order count.

The hotel confirmation number is `hotel_data.order_id`, not ETG's numeric `order_id`, our partner order ID or a supplier reference. When present, it is synchronized to the matching local RateHawk `Booking`. A missing HCN remains null and does not block cancellation or other post-booking operations. ETG says HCNs usually arrive within 48 hours, sometimes later, and recommends delayed retrieval every 24-48 hours within its stated 96-hour post-creation/pre-check-in windows. Retrieval here is on demand; no separate HCN scheduler was added. Keep the order confirmed while awaiting its HCN and arrange the recommended follow-up through the trusted operations workflow.

Before requesting cancellation, retrieve the order and present its current penalty and currency. For a verified Ziina checkout, an authorized operator must also obtain explicit consent for the amount to return to the customer in the **original charged currency**. For example, if the verified charge was 100.00 USD and the current supplier penalty was 0.00 USD, the private request body is:

```json
{
	"confirm_cancellation": true,
	"expected_penalty": { "amount": "0.00", "currency_code": "USD" },
	"confirm_customer_refund": true,
	"customer_refund": { "amount": "100.00", "currency_code": "USD" }
}
```

The values above are illustrative, not a price or policy. Copy the actual `current_penalty`; the supplier penalty amount must be a nonnegative decimal string. Authorize the customer refund separately; it must be positive, at most the verified charge, have at most two decimal places, and match its currency. The supplier's `amount_refunded`, penalty and payable amount are **not** instructions for the customer refund; verify any fees and partial-refund policy with the customer and finance before authorizing. The private caller must establish the customer's right to this order and capture that approval before sending these fields; the Bearer token alone is not per-customer authorization. For a legacy supplier booking with no linked verified checkout, omit both customer-refund fields; no Ziina refund is available through that route. The service refreshes order information, requires `status: completed` and `is_cancellable: true`, finds the single policy currently active in UTC, and compares penalty amount/currency exactly without floating-point conversion. Missing/overlapping policies or changed penalties fail closed. The policy is checked again after the durable claim, immediately before submission, to catch a cancellation cutoff crossed while saving. ETG's cancellation request accepts only `partner_order_id`, with no atomic maximum-penalty parameter; a supplier policy change or cutoff during the network request cannot be guaranteed away. Obtain explicit authorization for the financial risk and use ETG support for time-critical cases.

Non-refundable cancellation penalties are real outside the true sandbox. Upsells are NOT automatically cancelled; when the retrieved order includes them, `acknowledge_upsells: true` is required and the result keeps `upsells_require_manual_cancellation: true`. Contact `support@ratehawk.com` separately about cancelling those services. An already-cancelled order is recorded without another cancellation request.

`BookingCancellation` uses the partner order ID as its unique `_id` and stores a fingerprint of consent, the accepted penalty, the upsell acknowledgement and (for linked checkouts) the authorized customer-refund amount. It claims the checkout before contacting the supplier, barring a voucher worker that is sending or holds an unexpired lease; an uncertain confirmation email also requires review. The claim must persist before the request is sent. Identical concurrent/repeated requests return the saved operation; changed consent returns HTTP 409. If the confirmation/consent claim fails after recording the request, it is marked `cancel_failed` for operator review; do not resubmit the supplier mutation automatically. Transport retries, including automatic HTTP 429 retries, are disabled. Unknown/5xx responses, timeouts, `lock`, rate limits or malformed responses remain `cancel_pending`; definitive supplier errors such as `order_not_cancellable`, `order_not_found` and `sandbox_restriction` are recorded as `cancel_failed`. Do not infer failure or resubmit from an HTTP error after sending.

Pending cancellations are rechecked through order information by the existing MongoDB status worker, with leases across workers, a one-minute interval and respect for longer rate-limit delays. It resumes durable claims after restarts and never sends a second cancellation request. An unchanged `completed` order or temporarily empty order information remains pending. Monitor unresolved claims, database errors and `action_required`; operator reconciliation is required for definitive failures, interrupted requests or a policy change after the claim. This implementation deliberately does not offer an automatic retry/reset of a claimed cancellation.

Only a valid successful cancellation response or a retrieved `status: cancelled` updates local booking/process state to `cancelled` / `CANCELLED`. Delayed booking webhooks cannot reactivate that state. `amountRefunded`, `amountPayable` and `amountSell` preserve ETG's decimal strings and original currencies. They describe the supplier's accounting, not a completed refund to the customer's card. For a linked checkout with matching persisted consent, confirmed supplier cancellation moves it to `booking_cancelled`; the separate checkout worker saves a single Ziina refund ID before one `POST /refund` for the authorized amount. A timeout/unknown refund outcome is resolved through `GET /refund/{id}` only, without another POST. A verified `completed` GET marks the customer refund completed and queues its separate email. The private cancellation response reports `customer_refund_status: pending`, `completed` or `review` separately from supplier status; for legacy orders without a linked checkout it reports `not_processed`. A supplier refund amount is never automatically converted into a customer refund, and neither an uncertain cancellation nor a rejected one triggers a customer refund.

Keep `RATEHAWK_CANCELLATION_ENABLED` unset or false until authenticated ownership/consent handling, supplier permissions, cancellation penalties, MongoDB failover and customer-refund procedures are certified. Enabling cancellation is independent of enabling new bookings. Authenticated retrieval and reconciliation remain available when cancellation is disabled. The old `POST /api/v1/bookings/cancel` path is retired (410 after private authentication); it no longer accepts an unauthenticated reference or marks other suppliers cancelled without confirmation. Existing integrations using the formerly public order-info/cancel paths must migrate to private authentication; never put that Bearer token in the browser.

## ETG Midoffice Webhooks

Implemented the [Midoffice API](https://docs.emergingtravel.com/docs/midoffice-api/) [Webhooks](https://docs.emergingtravel.com/docs/midoffice-api/webhooks/) [Receive booking changes webhook](https://docs.emergingtravel.com/docs/midoffice-api/webhooks/receive-booking-changes-webhook/) as `POST /api/v1/webhooks/midoffice`. This is a separate contract from the B2B booking-status webhook at `/api/v1/webhooks/ratehawk`: its `data` contains `partner_order_id` (1-256 characters), optional `agreement_number`, and `type: "created" | "updated" | "cancelled"`, not `status: "completed" | "failed"`. Do not route these notifications to the booking-status handler or infer that a created or updated booking is confirmed.

ETG support must register the HTTPS callback URL for a Midoffice working with an Agency or TMC. Configure `ETG_MIDOFFICE_API_KEY` with the API Key token of the **Midoffice contract receiving the events**, separately from the B2B `RATEHAWK_API_KEY`; without it the callback fails closed with HTTP 500. Do not send an authorization Bearer token to ETG or put this API key in the callback URL, browser bundle, or logs. The handler requires `Content-Type: application/json`, a JSON body no larger than 8 KiB, and the documented envelope `{ "data": { "partner_order_id": "...", "type": "updated", "agreement_number": "..." }, "signature": { "timestamp": 1574146939, "token": "...", "signature": "<hex HMAC>" } }`. It verifies HMAC-SHA256 over the string `timestamp + token` using the configured Midoffice key with constant-time comparison. The optional agreement number is not an authorization decision; browser `Origin` and query parameters are rejected.

The signature does **not** cover the `data` object. Valid signed events are recorded as durable `MidofficeWebhook` receipts with a token digest, payload digest, partner order ID, event type, optional agreement number, and `action_required: reconcile_supplier_booking`; raw tokens and signatures are not stored. A second event with the same token and fields is acknowledged as a duplicate; changing fields under an existing token is rejected. ETG may retry signed events for days, so old timestamps remain acceptable; timestamps over five minutes in the future are rejected. Protect the receipt collection, retain it longer than the supplier's seven-day retry horizon and investigate conflicting replays. HTTP 200 means the receipt was persisted, **not** that the booking/payment was reconciled; ETG does not retry after 200. Storage failure returns HTTP 500 so ETG can retry after 30, 60, 90, 120, 150, and 300 seconds, then one hour, then every 12 hours for seven days (14 attempts in total, per ETG). Invalid signature, payload or replay returns 401, 400 or 409 respectively; those failures need operator diagnosis rather than a claim that delivery succeeded.

Receiving an event never calls ETG, changes a booking, issues a voucher, sends email, charges or refunds a customer. Each new receipt is saved as `pending` for reconciliation. The existing MongoDB status worker checks up to ten due receipts per tick **only** when `ETG_MIDOFFICE_RECONCILIATION_ENABLED=true`, which remains unset/false by default. After an atomic lease claim, it verifies that the partner order ID belongs to a local RateHawk booking process or booking, then retrieves exactly that order using the B2B account with one attempt and redacted request/response logs. It does not use the untrusted event `type` as supplier status and never updates bookings or payments. Unknown local IDs become `review_required: verify_midoffice_order_ownership`; confirmed supplier states become `review_required` with payment/refund follow-up instructions. Missing supplier orders or transient errors retry after at least 60 seconds (respecting longer supplier rate limits) and escalate to `verify_supplier_order_manually` after ten attempts. Unrecognized supplier statuses are recorded as `unknown`, not copied verbatim. Operators must monitor and resolve `review_required` receipts; this is read-only order reconciliation, **not** automated customer payment, refund or notification fulfillment.

Do not set the reconciliation flag until ETG confirms that `RATEHAWK_KEY_ID` / `RATEHAWK_API_KEY` can read the same orders delivered to the Midoffice contract, the locally stored partner IDs belong to those orders, and the receipt collection and indexes are durable and monitored. Register the callback URL with ETG support only after the signing key, MongoDB retention, replay handling and manual payment/refund procedure have been approved. Never copy an API key into the repository or return it in a support ticket. Offline tests mock ETG and MongoDB and use local HTTP only; no callback was registered, no key was set in deployment, and no live supplier or booking operation was made. Publishing code alone does not register or activate the integration.

## Frontend deployment

`frontend/src` is the source of truth. Express prefers `frontend/dist` when its `index.html` exists. Otherwise it serves only allowlisted public files and the `assets` directory from the committed repository-root site. Both modes support frontend routes without exposing server code, package files or private configuration. Missing API endpoints and assets return 404 rather than the application HTML.

The existing Render build command installs backend packages and Chrome, but does not build the nested frontend project. It can remain unchanged: the committed root site is the tested fallback when `frontend/dist` is absent. To build the frontend on the host instead, install the frontend's dependencies including dev dependencies, then run `npm run build` before starting the server. For a static host, publish the contents of `frontend/dist`, including manifest, icons, offline page and service worker.

For the existing repository-root static site, run `npm run build`, then `npm run prepare:site`. The preparation script copies only the built HTML, application assets, service worker, manifest, offline page and application icons into the root. It leaves `CNAME`, backend files and previous hashed assets untouched. `npm run check:site` verifies byte-for-byte agreement with the current build. These commands prepare local files only: they do not commit, push, deploy or enable payment collection. Backend changes must be deployed separately through the backend host after resolving the release blockers above.

The production preview uses the production API, not Vite's development proxy. The backend's exact CORS allowlist includes HTTP `localhost` and `127.0.0.1` on ports 10000, 5173 and 5178, in addition to the existing production origins. Deploy the backend change for these preview requests to work; rebuilding the frontend alone does not update CORS.

Autocomplete searches the local RateHawk content index and supplier multicomplete in parallel. NFKD/Arabic transliteration joins Arabic and Latin hotel spelling variants; indexed three-character tokens provide typo candidates, which are then ranked against the complete normalized names. The supplier is called in the selected API language and retried once in English only when it returns no hotel and region suggestions. Results report requested, resolved and supplier languages. Before release, deploy the backend and run `npm run sync:hotel-search-index` once to backfill indexed names/tokens; later hotel-content sync jobs maintain them. Use reviewed editorial aliases for brand names that cannot be safely transliterated. Supplier upserts do not write the editorial `translations` or `searchAliases` fields. MongoDB Atlas Search is not required for this implementation.

Hotel search and hotel-content requests accept `display_language` (`ar`, `en`, `es`) separately from `language`, which controls the supplier request. Responses expose requested and resolved language metadata. Live rates remain in the supplier-requested currency; display currency and estimated FX remain frontend-only and are not checkout inputs.

PWA cache v6 stores the offline page, app icons and same-origin hashed JS/CSS/fonts only. It does not cache API responses, checkout documents, guest information or external hotel photos. Offline mode cannot make reservations. Updates are user initiated outside checkout. Notification subscriptions and offline vouchers are not implemented.

The install control deliberately defers the browser's native banner with `beforeinstallprompt.preventDefault()` and calls `prompt()` after the user clicks install. Chrome's banner-suppression message is expected for this custom-install flow and is unrelated to destination requests.

## Measurement and experiments

The UI dispatches `remal:analytics` CustomEvents with an allowlisted name and numeric properties only. There is no analytics network transmission, tracker or experiment assignment by default. An approved consent-aware adapter can subscribe to these events; never add guest data, API credentials or booking hashes.

Events: `search_started`, `search_completed`, `search_failed`, `room_selected`, `checkout_started`, `payment_started`, `payment_failed`. Emit actual payment/booking completion only from verified server outcomes, not redirect pages or clicks. Production React is used in browser tests; development StrictMode may replay effect events.

Before A/B rollout, establish baseline confirmed-booking conversion per eligible search session, payment failure rate, price-change rate, contribution margin, cancellation and refunds. Proposed tests: compact search header versus the previous layout; total-stay price emphasis versus per-night emphasis with both always disclosed; supplier order versus price order. Predeclare sample size, minimum detectable effect, guardrails and stopping rules; assign users consistently. Do not experiment with truthful pricing or cancellation disclosure.

## Deliberate limitations

The interface is Arabic and live searches currently use USD, which the configured supplier accepts. Online collection remains disabled pending independent Sandbox and Production certification; the local Ziina implementation supports exact supplier-validated USD, AED, SAR or EUR deposits, not FX settlement. Nonfunctional login controls have been removed, not replaced with fake authentication. Real provider currency support, local wallets, cross-supplier entity/room matching, maps and verified review aggregation require provider data and separate tested integrations. Duplicate hotel IDs in one response are collapsed; this is not cross-supplier identity resolution.
